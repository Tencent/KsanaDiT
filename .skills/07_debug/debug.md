# 调试排查详细流程

> 核心原则：不猜测，用证据说话。每一步都基于可观测的数据做判断，不要在没有证据的情况下修改代码。

---

## 第 1 步：信息收集

在动手之前，先收集足够的信息。**禁止在信息不足时直接改代码。**

### 必收集项

1. **错误现象**：完整的错误信息、堆栈追踪
2. **环境信息**：GPU 数量、型号、CUDA 版本、Python 版本、Ray 版本
3. **复现条件**：哪个 workflow / pipeline / 命令触发？是否 100% 复现？
4. **最近变更**：最近改了什么代码？`git log --oneline -10`
5. **日志上下文**：错误前后 50 行日志，关注 warning 和 timing

### kDiT 特有收集项

| 场景 | 额外收集 |
|------|---------|
| tensor 相关 | tensor shape、dtype、device、是否 NaN/Inf |
| 分布式相关 | Ray dashboard、每个 GPU 的日志、NCCL 版本 |
| 内存相关 | `nvidia-smi`、`MemoryProfiler` 输出、OOM 前的内存曲线 |
| 推理结果异常 | 中间 latent 可视化、noise schedule 参数 |

**输出**：
- 信息收集清单（每项已收集 / 待收集）
- 初步现象描述（1-3 句话）

---

## 第 2 步：假设生成

基于收集到的信息，列出**所有可能的原因**，按可能性排序。

### 假设生成方法

1. **从错误信息出发** — 错误信息直接指向的模块
2. **从数据流出发** — 沿 kDiT 数据流追踪：ComfyUI Node → Engine → Executor → Generator → Model
3. **从变更出发** — 最近改的代码是否可能引入问题
4. **从环境出发** — 是否是环境差异（GPU 型号、driver 版本、依赖版本）

### 假设模板

```
假设 1（高可能性）：[模块] 的 [具体行为] 导致 [现象]
  - 支持证据：...
  - 验证方法：...

假设 2（中可能性）：...
假设 3（低可能性）：...
```

**输出**：
- 3-5 个排序假设，每个附带验证方法

---

## 第 3 步：逐层验证

按可能性从高到低验证假设，**每次只验证一个**。

### 验证工具箱

| 工具 | 场景 | 命令/方法 |
|------|------|---------|
| **日志分析** | 追踪执行流程 | `log.debug` / `log.info` 添加关键点 |
| **二分法** | 确定引入问题的变更 | `git bisect start` / 手动二分 |
| **最小复现** | 剥离无关因素 | 构造最简 workflow / 单 GPU 测试 |
| **tensor 检查** | shape / dtype / NaN | `print(t.shape, t.dtype, torch.isnan(t).any())` |
| **profiler** | 性能和内存 | `TimeProfiler` / `MemoryProfiler` / `nvidia-smi -l 1` |
| **隔离测试** | 排除模块交互 | 单独运行 Node / Generator / Model |

### 验证原则

- **最小成本优先** — 能看日志解决的不加断点，能加断点解决的不改代码
- **一次改一个变量** — 不要同时改多个东西然后测
- **记录每次验证结果** — 无论成功失败都要记录

**输出**：
- 每个假设的验证结果（已排除 / 已确认 / 待进一步验证）

---

## 第 4 步：定位根因

将验证结果收敛为明确的根因。

### 定位到的层级

| 层级 | 示例 |
|------|------|
| **模块级** | "问题在 Generator 的 denoise loop 中" |
| **函数级** | "问题在 `generator_runner.py:_run_denoise_step()`" |
| **行级** | "问题在 `generator_runner.py:178`，`latent_shape` 在 batch_size > 1 时多了一维" |

目标是尽量定位到**函数级或行级**。

### 根因分类

| 类型 | 说明 |
|------|------|
| 逻辑错误 | 代码逻辑不正确（条件判断、数据转换等） |
| 接口误用 | 调用方传参不符合被调用方预期 |
| 环境依赖 | 特定 GPU / driver / 依赖版本才触发 |
| 竞态条件 | 分布式 / 多线程环境下的时序问题 |
| 数据异常 | 输入数据超出预期范围（NaN、空 tensor、超大值） |

**输出**：
- 根因描述（文件:行号 + 原因分类 + 触发条件）

---

## 第 5 步：记录与移交

### 记录

输出调试结论，包含以下 4 项：

| # | 项目 | 内容 |
|---|------|------|
| 1 | **现象** | 用户可见的错误表现 |
| 2 | **根因** | 具体到函数/行的根因描述 + 分类 |
| 3 | **排查路径** | 列出的假设 → 验证过程 → 如何锁定 |
| 4 | **后续动作** | 需要修代码？转 `/kdit-bugfix`。需要优化？转 `/kdit-performance`。环境问题？给出配置建议 |

### 移交

根据根因决定后续：

| 根因类型 | 后续动作 |
|---------|---------|
| 逻辑错误 / 接口误用 | → `/kdit-bugfix` 修复 + 补回归测试 |
| 性能问题 | → `/kdit-performance` 优化 |
| 环境依赖 | → 记录到文档，给出环境要求 |
| 数据异常 | → 添加输入校验 + 错误提示 |
